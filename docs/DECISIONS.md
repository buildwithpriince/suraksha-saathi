# Decisions Log

Format: `D-XXX — Title (date) — Decision. Why. Alternatives rejected.` Append only; supersede, don't edit.

- **D-001 — Unity + AR Foundation for the app.** PS requires an APK with AR overlaid on real surroundings; needs ARCore plane detection and image tracking. WebAR rejected (no reliable plane AR on low-end Android, not an APK). React Native AR rejected (thin ecosystem, risky under time pressure).
- **D-002 — UI Toolkit with Advanced Text Generator, not TextMeshPro.** TMP does not shape Devanagari conjuncts/matras correctly; ATG uses HarfBuzz/ICU. Hindi and Santali are judged requirements.
- **D-003 — Scenario steps are data.** One generic ScenarioPlayer + JSON content lets us add modules without code, keeps safety content reviewable by non-programmers, and lets the engine be unit-tested.
- **D-004 — Local storage: SQLite.** Needed for transactional outbox. Candidate package: `gilzoide/unity-sqlite-net` (UPM, Android support). Fallback if it blocks us for > 2 hours: JSON files with atomic write + in-memory outbox index. Confirm in T-40 and record the outcome here.
- **D-005 — Two-level signature chain (root -> device attestation -> certificate).** Enables issuance AND verification with no network, which is a promised differentiator. Plain signed URL rejected (fails offline). Blockchain rejected (unnecessary; judges may see it as a buzzword).
- **D-006 — JWS-style compact tokens; verify over transmitted bytes.** Avoids cross-language JSON canonicalization bugs between C#, Python and TypeScript.
- **D-007 — Core C# tested with `dotnet test` outside Unity.** Fast feedback loop for Claude Code; Unity batchmode tests are slow and blocked when the Editor is open.
- **D-008 — Backend: FastAPI + Supabase Postgres on Render; dashboard on Vercel.** Matches team experience and the PPT.
- **D-009 — Generated content copy is not committed (2026-09-18).** `app-unity/Assets/StreamingAssets/content/` is gitignored; an Editor script (T-08) copies `/content` in on import and before every build. Keeps `/content` the single source of truth, so an APK can't ship stale scenarios. Committing the copy rejected (drifts silently whenever someone forgets to re-import).
- **D-010 — LF line endings everywhere; binaries in Git LFS except under `dashboard/` (2026-09-18).** `.gitattributes` sets `* text=auto eol=lf` (only `.bat`/`.cmd` are CRLF), so Windows clones (`core.autocrlf=true` by default) and macOS clones are byte-identical: Unity YAML stays LF for Smart Merge, and scenario JSON, string CSVs and `content/trust/*` read the same everywhere. Dashboard binaries stay in plain git because Vercel skips LFS files unless enabled per project. Relying on each teammate's `autocrlf` rejected (differs per machine).
- **D-011 — Health check is liveness only (2026-09-18).** `GET /v1/health` returns `{"status":"ok"}` without touching the database; it is Render's health-check path. A database outage then doesn't mark a working web process unhealthy, and tests don't need Postgres just to check the app is up. DB check in the same route rejected (couples liveness to Supabase; add a separate readiness check if needed). Unversioned `/healthz` rejected (docs/06 base path is `/v1`).
- **D-012 — Generic error codes come from the HTTP status (2026-09-18).** The app factory turns every error (404, 405, 422, unhandled 500s) into the docs/06 envelope, with the code list in docs/06; endpoints raise `ApiError(status, code, message)` for specific codes. 500s never include details. Unity sync client and dashboard see one error shape from the first endpoint on. Keeping FastAPI's default `{"detail": ...}` until T-51 rejected (clients would code against two shapes).
- **D-013 — Strict canonical base64url in every verifier (2026-09-18).** Decoders reject `=`, non-alphabet characters, impossible lengths and non-zero leftover bits (docs/04). Every byte string then has exactly one accepted spelling, and C# (T-13), Python (T-14) and TS (T-15) give the same status for the same garbled token. Lenient library defaults (optional padding, ignored leftover bits) rejected: several spellings of one token would verify, and implementations would drift.
- **D-014 — Root key formats; only a human generates the real key (2026-09-18).** `ROOT_SIGNING_KEY_B64` is base64url of the raw 32-byte seed; `root_public_key.txt` is one base64url line (docs/04 "Keys"). Same encoding as every other key and token segment, so one decoder serves all. `gen_root_key` writes the public key file, prints the seed once, and refuses to replace an existing key without `--force` (rotation invalidates every attestation and certificate). Claude never runs it for real, so the private key never enters a chat transcript (task T-17). Standard base64 and PKCS#8 rejected (a second decoder or a container format used nowhere else).
- **D-015 — Device public keys must be canonical prime-order Ed25519 points (2026-09-18).** Verifiers map any other `dpk` to `INVALID_ATTESTATION`, and registration (T-51) rejects such keys. RFC 8032 cofactorless verification (OpenSSL, BouncyCastle) accepts small-order keys: with the identity key, `R = identity, S = 0` verifies for any message, and since the attestation is public inside every QR, one such approval would let anyone mint valid certificates for that site. Honest keys are always prime-order, so nothing legitimate is lost. Found by the crypto review of T-14. Trusting the root admin to never approve a bad key rejected (a buggy device, e.g. an all-zero key buffer, would do it by accident).
- **D-016 — Scenario step schema: everything interaction-specific lives in `params` (2026-09-18).** Options are `params.options[]` (`id`, `labelKey`, `forbidden` + `tag`, `forbiddenVariants`); steps may carry `variants` (skipped elsewhere with `step_skipped`); any object may carry `needsReview`; `"$name"` substitution works at any depth in `params`; the params of each interaction type are tabled in docs/02. Keeps the documented step shape and gives T-10, T-16 and the player one contract. A separate top-level `options` field rejected (a second change to the step shape; params would still vary by type).
- **D-017 — Scoring clarifications for the module tables (2026-09-18).** `criticalOn: "forbidden"` encodes docs/02's "critical (if forbidden picked)"; multi-select without `partial` scores full only for the exact correct set ("all 4 required"); `zone_accuracy` reads the true radius from the step's `trueRadiusM`. Without `criticalOn`, docs/03's "earns 0 = critical failure" would fail a worker critically for picking CO2 on an ordinary fire, which docs/02 does not say. Making those rules non-critical rejected (breaks docs/03 tests 3 and 9).
- **D-018 — Safety gaps get spec-backed answers only (2026-09-18).** Where docs/02 is silent on a safety fact, scenario content uses only what the spec supports and flags the rest `needsReview` for the safety officer: extinguishers are ordinary `[water]`, oil `[dcp]`; CO2, and DCP on ordinary fires, score 0 without a critical failure until reviewed. Using common training guidance (ordinary `[water, dcp]`, oil `[dcp, co2]`) rejected: it would be invented safety content.
- **D-019 — Backend tests and Docker-less dev run on SQLite; production stays PostgreSQL (2026-09-18).** Docker isn't available on the dev machine used for T-50–T-56, so the models only use portable types (`Uuid`; JSON that becomes `jsonb` on PostgreSQL; `UuidList` that becomes `uuid[]`), and `app/db/engine.py` picks asyncpg for `postgresql://` URLs and aiosqlite for `sqlite:///` URLs. Each test gets a fresh SQLite file. `test_migrations.py` checks that Alembic's `upgrade head` builds exactly the models' schema, and `test_db.py` compiles the PostgreSQL DDL to check `jsonb`/`uuid[]`. Admin aggregates are computed in Python rather than with dialect-specific SQL (fine at prototype scale). Supabase is still the deployed database (D-008). Before relying on a new query, run `uv run pytest` once against `docker compose` Postgres (known gap: that hasn't been done yet). Requiring Docker for every test run rejected (it blocked this work). A PostgreSQL-only schema with SQLite skipped rejected (no local test coverage at all).
- **D-020 — Admin JWTs: JWKS asymmetric keys only; role from `admin_profiles` (2026-09-18).** backend/CLAUDE.md says "verify with the project JWKS", so the backend accepts ES256/RS256/EdDSA tokens with `aud=authenticated` and the project's issuer, and never HS256. That blocks algorithm-confusion attacks and means the server holds no shared secret. The role is read from `admin_profiles` (docs/05), not from JWT claims, so an admin grants dashboard access by adding a row. Supervisors get 403 on admin-only routes (device approval and listing, docs/08). The Supabase project must use JWT signing keys, not the legacy shared secret. Trusting a custom role claim rejected (needs a Supabase auth hook and duplicates `admin_profiles`). Accepting HS256 rejected (a leaked shared secret would let anyone mint admin tokens).
- **D-021 — Device request signing details (2026-09-18).** docs/05 names the signed fields but not their exact spelling, and the Unity client (T-57) has to match byte for byte. PATH excludes the query string; TIMESTAMP is the header text as sent (digits only, so `+1`, `1.0` and `1_000` are rejected rather than parsed); body hash is lowercase hex; signature is strict base64url (D-013). The signature is verified before the device's status is revealed, so an unsigned caller can't probe whether a device id is approved. There's no nonce: a replay inside the 300 s window is harmless because every device write is idempotent on client UUIDs. Server-side nonce storage rejected (state for no gain at prototype scale).
- **D-022 — Sync ingest edge cases and scorePercent rounding (2026-09-18).** Approved with the T-53 plan. (1) `round` in docs/03 is half away from zero; C# must pass `MidpointRounding.AwayFromZero`. C# and Python both round half to even by default, so without a pinned rule the device and server would disagree on scores like 92.5, and honest attempts would be flagged. (2) Per-item problems reject only that item (`invalid_payload`, `unknown_scenario`, `invalid_certificate`, all non-retryable), so one bad outbox row can't block a device's whole sync forever. Only a malformed envelope fails the request. (3) Workers must belong to the sending device's site. (4) The server stores its own recomputed `score_percent`/`passed`, keeps the device's claims in `result_json`, and flags every disagreement. Dashboards and certificates-due lists then never trust client-reported pass/fail (backend/CLAUDE.md). Criticality and max points come from the scenario file; per-rule `earned`/`passed` are trusted, because re-running the engine on events isn't possible without a Python port of docs/03. Whole-request 422 on any bad item rejected (a poison-pill outbox). Storing the device's numbers rejected (a tampered client would inflate compliance).
- **D-023 — SR1 lists are stored, re-signed on revoke, and cover every revoked cid (2026-09-18).** docs/06 says revoking "regenerates SR1", so each revoke re-signs the full list (sorted lowercase cids, `iat` = now) into a new `revocation_lists` row in the same transaction as the revocation. `GET /v1/revocations` serves the newest row; before any revocation it signs and stores an empty list, so devices always get a verifiable list rather than a 404. Revoking twice is a 200 no-op (a UI double-click must not error or change the recorded reason). Expired revoked certificates stay on the list, because an expired-but-revoked certificate should still read REVOKED (docs/04 checks revocation before expiry). Signing on every GET rejected (a new `iat` each time would make devices think the list changed). A diff-based list rejected (devices would need history to rebuild it).

- **D-028 — Hold samples, integer points and per-rule `passed` (2026-09-19).** Agreed 2026-09-18, pinned in docs/03 with T-12. `hold` reads each `hold_progress` as one 0.25 s sample: onTarget is the largest cumulative `onTargetSec` in the step, offTargetRatio is off-target samples over all samples in the step (so aiming at nothing counts against the ratio). Earned points are integers: "half" is `floor(points / 2)`, as `partial` already rounds down, so the result JSON never carries 7.5 and the server's sum matches. scorePercent is computed in integers, half away from zero (D-022). A critical rule's "its step" is `params.step`. Per-rule `passed` is "no critical failure" for critical rules and "full points" otherwise, which is what the backend recheck expects (a `criticalOn: "forbidden"` rule that earns 0 without a forbidden action is `passed: true`). Rejected: offTargetRatio over on+off samples only (would ignore spraying at nothing); fractional points (every consumer would need decimals).

- **D-031 — `mark_zone`, multi-select and gas presentation in camera mode (2026-09-19).** With T-30. docs/02 scores `zone_marked{radiusM}` against the step's `trueRadiusM`, but with direction-only anchoring (D-027) a tapped cone has no floor position. So each prefab carries a metre scale, `metresPerDeg` (ConfinedAreaEntrance: 0.15, so 10° = 1.5 m; gameplay tuning for T-33). A cone's distance is its angular distance from the hazard object times that scale, and `radiusM` is the mean over the placed cones (at least `minCones`; tapping a cone removes it). Each cone shows a simulated detector reading: `peakReading` at the source, falling linearly to `alertLevel` at `trueRadiusM`, with the levels taken from the `move_to` step whose `detector` approaches the same hazard. The worker then finds the alert boundary the way docs/02 describes ("places cones where the detector hits alert level"). The gas cloud is decoration on the leak with a fixed size, so it doesn't show the answer. `choose_many` and `checklist` are toggle cards with a Done button; Done with nothing picked is allowed and scored, because an empty choice is an answer. A `showRoute` step to a scene anchor points its arrow at the next waypoint (GAS_01 `retreat` runs behind the worker). Events and scoring are unchanged. With GAS_01 in `PLAYABLE_SCENARIO_IDS`, D-029's condition is met: certificates require passes in both FIRE_01 and GAS_01. Rejected: projecting taps onto the floor from an assumed phone height (fails above the horizon and mixes a second geometry model into the angular prefabs); scoring the nearest or farthest cone (one stray cone would decide the rule); drawing the cloud at the alert radius (the answer would be on screen).

- **D-033 — Steps can always be finished or skipped, and a skip scores as failed (2026-09-19).** On the GAS_01 retreat step, tapping the path mark did nothing and the run could not continue. From the code, several things could each cause that. (1) Only the highlighted next mark took taps; mark 2 and marks already reached were silently disabled. (2) The retreat marks sit 150–170° behind the placed overlay, so they only come on screen if heading tracking works (never on a phone without a rotation sensor, where `useCameraDirection` returns a fixed direction). (3) A mark could lie under the instruction card or bottom panel, which take the touch. (4) The round route arrow looks like a button but ignores touches. Fixes: any mark not yet reached takes a tap, and tapping one further along counts the ones before it (`core/player/waypoints.ts`; walking is not measured anyway, D-027). The next mark, the active tap target and the tabletop exit sign are pinned inside the free band between the card and the bottom panel (`clampToBand`, slightly faded when pinned), so they are always on screen and never under the chrome. Labels are laid out at least one label box apart on a 320 dp screen, and a test checks it. A step with no progress (no new event, no mark, cone or card tapped) for 30 s shows "Skip step (counts as failed)". It records `step_skipped` with `reason: "no_progress"`, and the engine scores every rule tied to the step as 0 and not passed, critical ones as critical failures (docs/03). Reusing `step_skipped` keeps the event types, backend and dashboard unchanged; a step inside the attempt's variant tells a worker skip from a variant skip. Skipping `place_on_plane` places the overlay where the camera points, because later steps need it and placement is not scored. Rejected: a new `step_failed` event type (every consumer would need a change for the same meaning); scoring a skip by leaving its rules to their normal checks (a `no_forbidden` rule would pay out for a skipped question, and hold samples recorded before the skip could still earn points); offering the skip immediately (too easy to use instead of trying).
- **D-034 — Worker ID card QR is `SW1:<worker uuid>`, unsigned (2026-09-19).** docs/00 D4 promises a worker ID card QR login at the kiosk, but no spec defined its contents. The QR text is `SW1:` followed by the worker's UUID in lowercase: nothing else, so a lost card shows no name. It follows the SS1/SA1/SR1 naming, but a colon keeps it from parsing as a docs/04 token. It identifies and does not authenticate: scanning it does exactly what tapping the worker in the Home list does, so signing it would add nothing. Cards are printed from the app with `expo-print` (offline; Android's print dialog can also save a PDF). The layout is bank-card size (85.6 × 54 mm) with a cut line, QR error correction Q for worn or laminated cards, and name, employee code and site as text. The QR SVG is built from `qrcode`'s module matrix, the library the certificate QR already uses. Rejected: a signed card token (no privilege to protect, and printed cards would break on key rotation); putting the name or employee code in the QR (personal data on a card that can be lost, for no gain); printing from the dashboard (it never sees app-enrolled workers until sync, T-57).
- **D-035 — Worker edit and soft delete; `deletedAt` in the worker sync item (2026-09-20).** Supervisors can change a worker's display name, employee code and preferred language, and delete a worker. docs/05 allows soft deletes only, but no table had a `deleted_at` column, so the device `workers` table gains one (SQLite migration 2) and the docs/06 worker item gains `deletedAt` (null, or the delete time, which equals `updatedAt`). The server `workers` table gets the same column in T-65; until then the backend drops the unknown field, so nothing breaks, but a delete does not reach the dashboard. Edits and deletes are `UPDATE`s with their outbox row in the same transaction, like every other change. The repositories contain no `DELETE FROM workers/attempts/certificates`, and a test checks it. Each change gets an `updatedAt` strictly after the previous one: the server keeps a worker change only if it is strictly newer (docs/05 LWW), and two changes in the same second would otherwise lose the second. An edit that changes nothing writes nothing. Deleting asks for confirmation in a native dialog. Certificates already issued keep the old name, because they are signed; the edit form says so. Enrol and edit share one form and one validation (`core/workers/edit.ts`). Rejected: a hard delete (breaks the references from attempts and certificates, and docs/05 forbids it); an "undelete" (no request for it, and LWW with a cleared `deletedAt` would need its own rules); hiding deleted workers only in the list (their ID card would still open them).
- **D-036 — Stabilised anchoring, marker correction, Reposition; FIRE_01 v2 in place (2026-09-28).** Placed overlays slid as the worker moved. Three causes, only one of them translation: (1) the linear mapping assumed a 50° wide preview, but expo-camera crops the 3:4 stream to fill a tall portrait screen, so about 32–35° is visible across a 20:9 phone and overlays moved at roughly two thirds of the scene's speed; (2) Android's rotation vector includes the compass, whose heading swings by tens of degrees near steel; (3) roll and the edges of the view were not projected. Now `core/orientationFilter.ts` propagates orientation with the gyroscope and pulls it towards the rotation vector (tilt τ 1 s, heading τ 8 s, snap above 60°; no gyroscope: an adaptive low-pass), and overlays use a full-quaternion pinhole projection whose focal length comes from `CAMERA_LONG_SIDE_FOV_DEG` (66°, tune in T-28) and the preview crop; taps use its exact inverse. Translation cannot be tracked without ARCore, so a scenario's `place_on_plane` may name an `anchorMarker` (FIRE_01: `HAZARD_A`, printed "FIRE HERE", laid on the floor): while ML Kit sees it, the anchor is blended onto its direction and the overlay scaled by its apparent size relative to the first sighting; sightings while turning faster than 40°/s are skipped because barcode results arrive late; out of frame, sensor anchoring continues from the last correction. The worker can re-place a drifted overlay with Reposition, recorded as `anchor_repositioned`, which no rule reads (a test inserts it into every step and checks the result is byte-identical); time spent repositioning still counts toward step time limits. Settings has a clearly labelled switch back to the original maths (raw rotation vector, 50° linear mapping, no marker) as a fallback until the new maths is proven on phones; it is stored in the secure store (a preference, not a secret) so no migration is needed. FIRE_01 is bumped to version 2 in place, with no frozen v1 file: the backend accepts only (id, version) pairs present in `content/scenarios/`, so once it is redeployed with this content, v1 FIRE_01 attempts are rejected as `unknown_scenario`, and until it is redeployed, v2 attempts are. - **D-039 — Measure the camera FOV on the phone; billboard overlays; make anchoring observable (2026-09-28).** The fire still slid when the phone turned after D-036. The overlay's rotation rate depends entirely on the preview's focal length, and D-036 assumed a 66° lens. expo-camera 57 exposes no focal length, FOV or sensor size (its JS API offers picture sizes and lens names only), so the FOV cannot be queried; it is now measured. The hidden calibration screen (long-press Settings on Home) has the worker aim the centre ring at a real object and turn until the object sits on a guide line; the gyroscope, integrated between the two marks, gives the exact device rotation, and the pinhole model then fixes the focal length (`core/calibration.ts`, exact for any pitch or roll during the turn; a 5 px alignment slip moves it by under 4%). The worker averages a few turns and saves; training uses the calibrated lens FOV, else the default, and shows which. The view geometry now comes from the camera view's measured layout, not the window, which can differ by the system bars. Why not a 90° turn for calibration: the visible width is only about 33°, so an object turned 90° is off screen and its pixel offset cannot be read; the 90° turn is used by the self-test instead, which measures how far the orientation estimate drifts over a rotate-away-and-return, for the anchoring in use and for the raw rotation sensor side by side. The filter now corrects heading towards the compass only while turning slower than 20°/s: in a simulated round trip with a 15° compass error met mid-turn it returned within 3° instead of 6.9°. Overlays are billboards (`core/player/overlay.ts`): the anchor gives screen position only, so the flame stays upright on screen whatever the roll (D-036 had kept it upright in the world instead). A status line in every drill shows MARKER LOCK / SENSOR / LEGACY and whether a gyroscope was found; Settings can turn on a debug overlay with the FOV in use and its source, the view size and focal length, the filter-vs-raw disagreement (which would expose a gyro axis or sign error as a large value during turns), and the last marker residual (the real drift the marker removed). Marker detection runs through the whole drill; the only throttle is expo-camera dropping a barcode result identical to the previous one within 500 ms, so the lock indicator now waits 1.2 s before showing a lost lock.
